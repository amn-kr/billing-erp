# Deployment (live app)

Set up by the owner by hand on 5 Oct 2026, on free plans. **No secrets are written here** — passwords and
connection strings live only in Render, Neon and GitHub settings.

> ⚠️ **Anything merged into `main` goes live within minutes.** Render rebuilds both services on every
> change to `main`, and the server's build **runs the database migrations** on the live database.
> Merge only when the checks pass, and treat any pull request with a new migration (`apps/api/prisma/migrations/…`)
> as a change to the live books: take a fresh backup first (see *Backups* below).

## What runs where

| Part | Service (free plan) | Name / address | Region |
|---|---|---|---|
| Screens (web app) | Render **Static Site** | `billing-erp` — https://billing-erp-ynqf.onrender.com | — (CDN) |
| Server (API) | Render **Web Service** | `billing-erp-api` — https://billing-erp-api.onrender.com | Singapore |

The screens and the server are reached through **one address** (the static site): requests to `/api/*` are
passed on to the server, so the sign-in cookie works. (Cloudflare was not used; the owner's Cloudflare
account is unused for now.)

## Database (Neon)
- Two roles:
  - `neondb_owner` — owns the tables; runs the migrations; used for backups. Neon gives it the right to read past row-level security (`BYPASSRLS`), so it must never be the app's connection.
  - `erp_app` — the API's role, created by the owner in the Neon SQL Editor (`CREATE ROLE erp_app WITH LOGIN PASSWORD '…'`), `rolbypassrls = false`. Row-level security applies to it: each request only sees its own shop.
- The API connects **directly** (connection pooling off), because it sets the shop for each request inside a transaction.

## Server (Render Web Service `billing-erp-api`)
- Branch `main`, auto-deploy on.
- Build: `npm install -g pnpm@10.28.0 && pnpm install --frozen-lockfile && pnpm exec turbo run build --filter=@billing/api && pnpm --filter @billing/api db:migrate`
- Start: `cd apps/api && NODE_ENV=production node dist/main.js`
- Health check: `/api/health`
- Environment variables (values are secret): `NODE_VERSION=22`, `DATABASE_URL` (erp_app), `MIGRATE_DATABASE_URL` (neondb_owner), `JWT_SECRET` (generated by Render), `COOKIE_SECURE=true`, `TRIAL_DAYS=14`, `DEMO_ENABLED=false`, `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`, `WEB_ORIGINS=https://billing-erp-ynqf.onrender.com`

## Screens (Render Static Site `billing-erp`)
- Branch `main`, auto-deploy on.
- Build: `npm install -g pnpm@10.28.0 && pnpm install --frozen-lockfile && pnpm exec turbo run build --filter=@billing/web`
- Publish directory: `apps/web/dist`
- Rewrites, in this order: `/api/*` → `https://billing-erp-api.onrender.com/api/*`; `/login` → `/login.html`; `/*` → `/index.html`

## GitHub
- Dependency graph, Dependabot alerts, Dependabot security updates and grouped security updates are on.
- CI (`.github/workflows/ci.yml`) runs every test on each pull request (about 45 minutes); merge only when it is green.

## Backups
The workflow **Daily database backup** (`.github/workflows/db-backup.yml`) runs every night at 03:00 India
time, and whenever started by hand (GitHub › Actions › *Daily database backup* › *Run workflow*). Each run:
1. checks row-level security on the live database as `erp_app` (read-only: no shop's rows are visible without choosing that shop);
2. takes a full backup with `pg_dump` as `neondb_owner`, **encrypted with a passphrase** (AES-256), and keeps it in the run for **30 days**;
3. restores that backup into an empty throwaway database on GitHub's machine and checks it: every migration and table is there, row-level security is still on, and shop by shop no shop can see another shop's rows. The live database is never written to.

If a run fails, GitHub emails the owner and the run shows red under Actions.

### One-time setup (owner)
Add three repository secrets in GitHub › the repository › Settings › Secrets and variables › Actions › *New repository secret*:

| Secret | Value |
|---|---|
| `NEON_BACKUP_URL` | the Neon connection string for **neondb_owner** (Neon › Connect › role `neondb_owner`, pooling off) |
| `NEON_APP_URL` | the Neon connection string for **erp_app** (the same one as Render's `DATABASE_URL`) |
| `BACKUP_PASSPHRASE` | a long passphrase you make up (e.g. five random words). **Write it down somewhere safe outside GitHub** — without it the backups cannot be opened. |

Then run the workflow once by hand and check it goes green.

### Restoring (in an emergency)
1. GitHub › Actions › *Daily database backup* › pick a green run › download the `db-backup-…` file and unzip it (`billing-erp-YYYY-MM-DD-HHMM.dump.gpg`).
2. Decrypt: `gpg --decrypt --output db.dump billing-erp-….dump.gpg` (asks for the passphrase).
3. In Neon, create a **new branch** (or a new project) to restore into — never restore over the live branch while the app is running.
4. Restore: `pg_restore --no-owner --dbname="<connection string of the new branch, neondb_owner>" db.dump`, then create the `erp_app` role there if it is a new project, and point Render's `DATABASE_URL` / `MIGRATE_DATABASE_URL` at it.

Neon itself can also go back in time on its own, but on the free plan only a few hours back (see *Limits*). The nightly backups go back 30 days.

The scripts behind this are in `infra/db/backup/` and can be run on any computer with Postgres 16 tools.

## Real-time backup (each shop's own copy)
Separate from the nightly whole-database backup above: each shop's books are copied to the place the
shop owner chooses (Google Drive, this computer, or both), about a minute behind, plus a full copy each day.
- Every save also writes its change to the table `change_log`, in the same transaction (a database trigger on every shop table).
- While the server is awake, it sends each place the changes it hasn't confirmed yet, every minute, as a compressed
  file locked with AES-256. A file counts as sent only once the place confirms it; if the place is down, it tries again
  after 1, 2, 4, 8 and then every 15 minutes, and nothing is skipped.
- Restore puts the backup into **new books** (like *Start fresh*): the current books are never overwritten.
- Old backup files and old rows of `change_log` are **not deleted yet**; the rule for that comes later, with the owner's approval.

### One-time setup (owner)
In Render › `billing-erp-api` › *Environment*, add `BACKUP_MASTER_KEY`: click *Generate* for a random value, save,
then **copy the value into the same safe place as `BACKUP_PASSPHRASE`**. Every backup file is locked with this key
(each shop with its own key made from it): if it is lost or changed, the backups made with it can't be opened.
Never paste it into chat, email or GitHub. Until it is set, the server sends no backups (it says so in its log).
Optional: `DB_SPACE_LIMIT_MB` (default 500, Neon's free plan) for the "space for your books" warning.

### Google Drive (one-time setup, owner; free)
The app asks Google only for **"files this app created"** (`drive.file`, which Google classes as non-sensitive): no Google
review and no "unverified app" warning, and the app sees nothing in a Drive except its own folder
"Billing ERP Backup - <shop>". Google's login for each shop is kept locked on the server (with a key made from
`BACKUP_MASTER_KEY`); it is never shown, logged or written to the activity log. **Do not add a card or start a free
trial in Google Cloud: nothing here needs billing.**
1. console.cloud.google.com › project picker › **New project** `Billing ERP` › **Create**, then select it.
2. Search **Google Drive API** › **Enable**.
3. Search **Google Auth Platform** › **Get started**: app name `Billing ERP`, your support email › **Next** ›
   Audience **External** › **Next** › contact email › **Next** › tick *I agree* › **Continue** › **Create**.
4. **Data Access** › **Add or remove scopes** › filter `drive.file` › tick only `…/auth/drive.file` › **Update** › **Save**.
5. **Clients** › **+ Create client** › *Web application*, name `Billing ERP server`, **Authorized redirect URIs** ›
   **+ Add URI** › `https://billing-erp-ynqf.onrender.com/api/backup/drive/callback` › **Create** › **Download JSON** (keep it safe).
6. **Audience** › **Publish app** › **Confirm**: the status must read **In production** (in "Testing", Google ends the
   connection every 7 days). Brand verification (app name and logo on Google's screen) is skipped for now.
7. Render › `billing-erp-api` › **Environment** › add `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from the
   JSON file › **Save Changes**. Until both are set, "Connect Google Drive" says Drive isn't set up on this server.

### For developers
A migration that writes shop rows without a shop chosen lifts `FORCE ROW LEVEL SECURITY` on the tables it fills;
it must lift it on `change_log` too, or the trigger's insert is refused. A new shop table gets the trigger like this
(an API test fails until it has it): `CREATE TRIGGER <table>_backup AFTER INSERT OR UPDATE OR DELETE ON <table> FOR EACH ROW EXECUTE FUNCTION log_change('business_id');`

## Limits of the free setup (as checked on 9 Oct 2026; they can change)
- **The server sleeps.** Render's free web service stops after 15 minutes without visits; the next visit wakes it in about a minute. Render gives 750 free hours a month per workspace (a sleeping server uses none); if they run out, free services stop until the next month.
- **Database size: 0.5 GB** per Neon project on the free plan, and 100 compute-hours a month; Neon's computer also sleeps after 5 minutes idle (wakes in a moment). If a monthly limit is reached, the database stops until the next month.
- **Neon's own restore window is short** on the free plan (about 6 hours back) — that is why the nightly backups exist.
- **GitHub storage for backups:** a private repository on the free plan has a limited amount of storage for workflow files (500 MB); one encrypted backup of a small shop is well under 1 MB, kept 30 days.
- **No uptime promise and no support** on free plans.
- **Files on the server are not kept** (Render wipes them when it sleeps) — the app stores everything in the database, so this does not lose data.
